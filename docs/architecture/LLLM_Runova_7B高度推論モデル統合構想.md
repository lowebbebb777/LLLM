## 0. この文書の扱い

この文書は、LLLMとRunovaを一つの長期研究開発として整理するためのものである。

ただし、過去に壮大な理念や将来の他者展開を先回りした結果、実装担当AIがセキュリティ、抽象化、汎用化、安定化を過剰に優先し、肝心の能力実現が進まなかった経験がある。

したがって、本書では次を厳守する。

1. **理念は方向を定めるが、現在の実装範囲を拡大する根拠にしない。**
2. **能力実現を最優先する。**
3. **各仮説は、比較実験と数値で判定する。**
4. **未検証の構想を、実現済みの能力として扱わない。**
5. **将来の公開、販売、複数利用者、企業運用を先回りして設計しない。**
6. **Claude CodeやCodexは、現在指定された小さなマイルストーンだけを実装する。**

本書の上位思想は、実装担当AIに大規模な基盤やセキュリティ機構を作らせるためのものではない。現在の技術判断では、後述する「実装優先順位」「実験ゲート」「非目標」が優先される。

## 1. 一行定義

> **LLLMは、小型ローカルモデル自身の内部表現と推論能力を改良する研究であり、Runovaは、その小型モデルが外部記憶、観測、実行、検証、失敗修復を利用して高度なソフトウェア開発を継続できるようにする実行環境である。**

両者は別々のプロジェクトではない。

- Runovaが実タスク、失敗、修復、検証結果を生成する。
- LLLMがその経験を学習可能な形に変え、小型モデルへ内在化する。
- 改良された小型モデルが、次のRunova開発と実タスク処理を改善する。

この循環を成立させることが最終的な狙いである。

## 2. なぜ7B級で行うのか

### 2.1 7Bは妥協ではなく、研究対象である

本構想において、7B級モデルは「大きなモデルを購入できないため仕方なく使うモデル」ではない。

大規模モデルと高価なGPUを前提にすれば、一定の能力は購入できる。しかし、それでは次の問いに答えられない。

> 限られた計算資源と小型モデルでも、正しい外部構造、学習方法、推論ループ、検証機構を与えれば、高度なアプリケーション開発を継続できるのではないか。

この問い自体に研究価値がある。

### 2.2 普及可能なハードウェアを基準にする

現在の主な実機条件は次である。

- CPU: Intel Core i7-11700
- RAM: 32GB
- GPU: NVIDIA GeForce RTX 3060 12GB
- Storage: 約7.32TB
- OS: Windows 11を中心とし、必要に応じてUbuntu系環境を使用

この条件で実行・学習できる7B級モデルを基準にすることで、研究成果が特別な計算機だけに閉じない。

### 2.3 民主化は先に宣言する成果ではない

長期的な意図は、専門知識と作りたいものを持つ人が、大資本や大規模組織を持たなくても、高性能かつ大規模なアプリを作れる状態へ近づけることである。

しかし「7Bで動いた」だけではAIの民主化を達成したとは言えない。

最低でも、次を実測する必要がある。

- 一般的なPCで動くこと
- 高価なWeb AIの常時利用を必要としないこと
- 実用的な原子的タスク成功率があること
- 長時間の無人実行で破壊的な変更を起こさないこと
- 失敗から復旧または安全停止できること
- 利用者の知識を、再利用可能なタスク、証拠、テストへ変換できること

したがって民主化は実装要件を肥大化させる理念ではなく、実験結果から後で判定される成果である。

## 3. 本人が実現したいこと

### 3.1 高性能Web AIを静的に使う

GPT、Claude、その他の大規模Web AIは、次の低頻度で静的な処理に使う。

- 大目的の分析
- マイルストーン分解
- 変更セット設計
- 原子的タスクへの分解
- 最新技術情報の調査
- DOM、Web画面、外部サービス仕様の観測
- ローカルモデルが解決できない設計問題の再設計
- 学習データの教師候補生成

出力は会話のまま消費せず、次のような固定成果物にする。

- `campaign_plan.json`
- `change_set_plan.json`
- `atomic_tasks.jsonl`
- `evidence_bundle.json`
- `replan_response.json`
- 教師軌跡データ

Web AIがRunovaの実行ループへ常時参加し、毎回DOMを操作しながら次の行動を決める構造にはしない。

### 3.2 動的に動く主体をローカルへ限定する

頻繁に繰り返される動的処理は、原則としてローカルで行う。

- リポジトリ探索
- 関連ファイル読取
- パッチ生成
- テスト追加
- コンパイルエラー修正
- テスト失敗分析
- 局所的な再試行
- 差分説明

ここを7B級ローカルモデルに担当させる。

### 3.3 DOMと外部ツールを中核から外す

外部Web UIやDOM操作は壊れやすい。

- 要素構造が変わる
- セッションが切れる
- レート制限が変わる
- ブラウザ状態に依存する
- 外部サービスの仕様変更で停止する

したがってDOMや外部ツールは、Runovaの状態管理、長期記憶、タスク正本、コード変更権限を持たない「観測端」とする。

```
Web / DOM / 外部仕様
        ↓ 観測
Evidence Packet / Fixture / Contract
        ↓
RunovaのローカルTask Graph
        ↓
7Bローカルモデルによる実装
        ↓
ローカル検証
```

一度取得した外部情報は、可能な限り次へ変換する。

- HTML/DOM fixture
- API response fixture
- semantic selector contract
- record/replayデータ
- 公式仕様の要約と出典
- バージョン付きEvidence Packet

これにより、二回目以降の実装とテストをローカル化する。

### 3.4 一日放置しても進む安定性

狙うのは、AIが無制限に動き続ける状態ではない。

> 翌朝、検証済みコミットが積み上がっているか、明確な理由を記録して安全停止している状態

を成立させる。

速度も必要だが、優先順位は次である。

1. 破壊しない
2. 状態を失わない
3. 無限反復しない
4. 検証済み成果だけを確定する
5. 再起動後に続行できる
6. その上で速度を上げる

### 3.5 小型モデル自身を育てる

Runovaだけを賢くし、モデルを永遠に交換可能な作業員として扱うのではない。

Runovaの実行経験を利用して、7Bモデル自身に次の能力を学ばせる。

- 必要な観測の選択
- 仮説の生成
- ファイル選択
- ツール選択
- テスト結果の解釈
- 同一失敗の認識
- 修復方針の変更
- rollback判断
- 上位AIへ昇格すべき状況の認識

目標は長い思考文を出すモデルではなく、実行結果を受けて行動を変えられるモデルである。

## 4. LLLMリポジトリの現状

対象リポジトリは `lowebbebb777/LLLM` であり、現在の主要実装は `varlora/` 以下にある。

### 4.1 現在の研究テーマ: VariationalLoRA

VariationalLoRAは、本人が過去に開発した動的弾塑性き裂進展解析プログラムと有限要素法の変分原理から着想した独自LoRAアダプタである。

中心的な構造は、標準LoRAの単一低ランク経路ではなく、二つの経路を入力依存ゲートで統合することである。

| FEM側の概念 | VariationalLoRA側 |
|---|---|
| 連続場 | `cont_A → cont_B` |
| 離散場・節点自由度 | `disc_A → disc_B` |
| 形状関数、分割の単位性 | `shape_fn → softmax` |
| ガウス求積 | `quad_weights` |
| 連続場と離散場の整合 | `qw * cont + (1 - qw) * disc` |

概略は次である。

```python
cont = cont_B(cont_A(x))
disc = disc_B(disc_A(x))
N = softmax(shape_fn(x) / tau)
qw = sum(N * quad_weights)
out = qw * cont + (1 - qw) * disc
```

### 4.2 適用条件

現在のSPECでは次を採用している。

- ベースモデル: `Qwen/Qwen2.5-Coder-7B`
- 適用対象: FFN層の`gate_proj`、`up_proj`、`down_proj`
- Attention層には適用しない
- 4bit NF4によるQLoRA構成
- gradient checkpointing
- gradient clipping
- PagedAdamW8bit優先
- NaN/Inf検出とダンプ
- ゲート値の監視

### 4.3 交絡を排したA/B/C/D実験

本研究の重要な点は、独自機構を実装しただけで効果を主張しないことである。

| 条件 | 内容 | 判定目的 |
|---|---|---|
| A | 標準LoRA、基準rank | 通常ベースライン |
| B | 標準LoRA、Cと総パラメータ数を一致 | パラメータ増加効果を分離 |
| C | VariationalLoRA、動的ゲート | 本仮説 |
| D | VariationalLoRA、固定ゲート | 動的ゲートの寄与を分離 |

仮説成立の最低条件は次である。

```text
C > B かつ C > D
```

- `C > A`だけでは、単にパラメータが増えた可能性がある。
- `C ≈ B`なら、変分構造の効果ではない。
- `C ≈ D`なら、動的ゲートは不要である可能性が高い。

### 4.4 評価軸

現在のSPECには次がある。

- HumanEval
- MBPP
- pass@k
- 数値・統計問題の独自評価セット
- 数値整合性
- 効果量
- 複数seed
- 経路独立性スコア

経路独立性は、有限要素法・J積分に由来する着想である。

同じ問題に対して、言い換え、手順変更、中間表現変更など異なる経路を与えても、同じ正解へ到達できるかを測る。

これは表面的なベンチマーク点数だけでなく、内部表現の頑健性を評価する軸として重要である。

### 4.5 M0の実機結果

RTX 3060 12GB上で、条件C、約500件、1 epochのM0が実行され、次が確認されている。

- OOMなし
- loss: 1.91から約0.5へ低下
- 63 optimizer updates
- NaNなし
- ゲートの0/1張り付きなし
- 4bit、PagedAdamW8bit、gradient checkpointingで実行可能

したがって、少なくとも「RTX 3060上でVariationalLoRAを学習ループへ載せられる」というM0能力は成立している。

### 4.6 ゲートに関する重要な発見

最初の実機結果では、`qw_mean`が約0.333付近で安定し、`quad_weights`もほぼ一様のままだった。

これは数値的に安定している一方、動的ゲートが実質的に動いていない可能性を示した。

理由は次である。

- `N = softmax(...)`なので`sum(N)=1`
- `quad_weights`がすべて`1/n_quad`の一様値なら、`qw=1/n_quad`へ固定される
- ゲート側は数百程度のパラメータである
- cont/disc経路は約6200万パラメータ規模である
- 同じlearning rateでは、ゲートの更新が相対的に小さすぎる
- cont/discのB行列がゼロ初期化されるため、開始直後のゲート勾配も弱い

これに対して、ゲート用パラメータを別optimizer groupへ分け、`gate_lr_multiplier=10`を与える変更が入っている。

1倍から10倍へ変更したとき、`qw_mean`の移動量が約`-0.001`から`-0.009`へ増え、勾配経路が生きていることは確認された。

ただし、これは「動的ゲートが性能向上に寄与した」ことをまだ証明していない。M1の長い学習とA/B/C/D比較が必要である。

### 4.7 テスト状態

最新コミットでは、ゲート用optimizer groupのテスト2件を追加し、CPUテストは合計35件すべて成功したと記録されている。

### 4.8 現在のドキュメント不整合

`varlora/README.md`には、最新結果と古い状態説明が混在している。

- 上部には「RTX 3060でM0実機確認が必要」と残っている
- 下部には「M0合格」と記録されている
- テスト件数が33と記載されている箇所がある
- 最新コミットでは35件成功である

実装そのものの問題ではないが、AIが古い記述を正本と誤認する危険がある。

次回の小さなドキュメント修正では、最低限次を行う。

1. M0状態を「合格済み」へ統一
2. テスト件数を35へ統一

## 5. 統合研究仮説

LLLMとRunovaを統合する研究は、少なくとも四つの別仮説に分ける必要がある。

### H1: VariationalLoRA仮説

FEM由来の連続・離散二経路と動的ゲートが、同じパラメータ数の標準LoRAより、コード生成、数値整合性、経路独立性を改善する。

判定:

- CがBを上回る
- CがDを上回る
- 複数seedで再現する
- 効果量がノイズ範囲を超える

### H2: Runova外部推論器仮説

7Bモデル単体では困難な問題でも、タスク分解、外部記憶、コード検索、テスト、失敗履歴、状態機械を与えることで、システム全体として高い問題解決能力を得られる。

判定:

- 同一7Bモデルの単発回答よりRunova経由の成功率が高い
- 不要変更率が下がる
- 同一失敗反復率が下がる
- 長時間実行の安全停止率が上がる

### H3: Runova経験蒸留仮説

Runovaで得られた成功、失敗、修復、rollback、昇格判断の構造化軌跡を学習させることで、7Bモデル自身のツール利用と修復推論が改善する。

判定:

- 未学習の実タスクでAtomicTask成功率が上がる
- 平均試行回数が下がる
- Web AIへの昇格率が下がる
- 誤った自信による破壊的変更が減る

### H4: 静的Web AI・動的ローカル分離仮説

高性能Web AIを計画、調査、教師生成に限定し、動的な実行をローカル7Bへ集約しても、実用的な開発速度と品質を維持できる。

判定:

- Web AI呼び出し回数を大幅に減らせる
- Web AI不在時にも既存Task Graphを継続できる
- ローカル処理だけで完了するタスク比率が増える
- 一日相当の実行で検証済み成果または明確なBLOCKED状態が残る

### 5.1 モデル能力とシステム能力を混同しない

評価では次を分ける。

#### モデル内在能力

- 単発のコード生成
- 観測後の次行動選択
- エラー分類
- 修復方針
- 経路独立性
- LoRA適用による性能差

#### Runova込みのシステム能力

- タスク分解
- 必要コンテキスト選別
- 状態保持
- テスト実行
- rollback
- Watchdog
- 永続化
- 長時間継続

7Bモデルが大規模モデルと同じ内部知識を持たなくても、外部構造を使って同等の実務結果へ近づける可能性はある。

一方、Runovaがすべて判断し、7Bが単なる定型パッチ生成器のままであれば、モデル自身の高度推論開発という目標は達成していない。

両方を別々に測定する。

### 6.1 ControllerはAIにしない

長時間安定性をモデルの知性へ依存させない。

Controllerが決定論的に行う。

- 現在タスクの選択
- WIP=1の強制
- コンテキストサイズ制限
- allowed filesの強制
- コマンドtimeout
- プロセス終了
- 最大試行回数
- 同一失敗fingerprint
- checkpoint
- rollback
- 検証成功後のcommit
- 再起動時の復旧

7Bモデルは、限られた状態の中で次の良い行動を提案する。

### 6.2 Web AI同士を自由討論させない

Web AIとローカルAIの連携は、会話の往復ではなく構造化パケットで行う。

```json
{
  "task_id": "T-042",
  "objective": "BrowserProviderの起動方式を更新する",
  "allowed_files": [
    "runova/providers/browser.py",
    "tests/test_browser_provider.py"
  ],
  "invariants": [
    "既存CLI引数を変更しない"
  ],
  "evidence_refs": ["R-019"],
  "acceptance_criteria": [
    "対象テストが成功する"
  ],
  "escalation_conditions": [
    "公開インターフェース変更が必要",
    "allowed_files外の変更が必要"
  ]
}
```

自由討論は、コスト、再現性、状態追跡、責任分界を悪化させる。

### 6.3 小型モデルの自由度を段階的に上げる

初期段階では、7Bへ与える自由度を小さくする。

#### Level 1

- ファイル指定済み
- 変更内容指定済み
- テスト指定済み
- パッチ生成のみ

#### Level 2

- 関連ファイル探索を許可
- 1〜3ファイル
- 局所エラー修復を許可

#### Level 3

- 小規模ChangeSet
- テスト追加
- 数回の自律再試行

#### Level 4

- 変更セット内部の再分解
- 証拠要求
- 上位AIへの昇格判断

レベルはモデル名で決めず、固定ベンチマークの実績で昇格させる。

### 7.2 自由な内部思考文を正典にしない

学習データとして重要なのは、長い独白ではなく、観測と行動の関係である。

```json
{
  "task_id": "T-001",
  "observation": "Configにui_themeが存在しない",
  "hypothesis_summary": "フィールドと保存対象一覧の両方が必要",
  "action": {
    "type": "read_file",
    "target": "runova/config.py"
  },
  "result": {
    "status": "evidence_found",
    "summary": "保存側に明示的な項目一覧がある"
  },
  "next_action": {
    "type": "edit",
    "targets": [
      "runova/config.py",
      "runova/config_docs.py"
    ]
  }
}
```

保存するのは監査可能な理由要約であり、未検証の長文推論そのものではない。

### 7.3 成功だけを学習させない

次のデータを区別する。

- 一回で成功した軌跡
- 失敗を正しく認識し修復した軌跡
- 同一失敗を反復した軌跡
- テストを弱体化して見かけ上通した軌跡
- 許可外ファイルへ変更した軌跡
- 適切にrollbackした軌跡
- 適切に上位AIへ昇格した軌跡

「失敗しないモデル」より「失敗を誤魔化さず修復できるモデル」を育てる。

### 7.4 教師データの作成

高性能Web AIは教師候補を生成するが、教師の回答をそのまま正解としない。

```
教師候補
   ↓
Runova実環境で実行
   ↓
コンパイル・テスト・制約検証
   ↓
採用 / 不採用 / 修復
   ↓
検証済み教師軌跡
```

これにより、文章として説得力があるだけの誤答を学習データへ混入しにくくする。

## 8. LLLMモデル開発の段階

### Phase 0: 現状の正本化

- READMEのM0状態を更新
- テスト件数を35へ統一
- 実験結果保存形式を統一
- commit hash、config、seed、環境情報を結果へ付与
- M0の再現コマンドを固定

完了条件:

- 別のAIがREADMEとSPECだけを読み、現在地を誤認しない

### Phase 1: VariationalLoRA M1

- A/B/C/Dを各3seed以上
- 学習データ、epoch、optimizer、評価条件を固定
- 条件BとCの学習可能パラメータ数を記録
- gate LR倍率を実験変数として管理
- 数値整合性と経路独立性を評価

完了条件:

- C、B、Dの差を平均、標準偏差、効果量で説明できる

### Phase 2: M2判定

判定分岐:

#### C > B かつ C > D

VariationalLoRA仮説を暫定採用し、Runova軌跡学習へ適用する。

#### C ≈ B

二経路構造の性能差は主にパラメータ増加と判断する。機構を増やさず、簡素化または別仮説へ進む。

#### C ≈ D

動的ゲートの価値が確認できない。固定混合または異なるゲート設計を検討する。

#### C < B

現構造を不採用とする可能性を認める。思想を守るために結果を捻じ曲げない。

### Phase 3: Runova固定ベンチマーク

実リポジトリから、難易度別に100件程度のAtomicTaskを固定する。

例:

- 設定項目追加
- 小規模バグ修正
- テスト追加
- ログ追加
- 型修正
- 既存関数分割
- UIの限定変更
- ビルドエラー修復
- 複数ファイル整合

各タスクには正解コードだけでなく、次を持たせる。

- 初期commit
- task contract
- allowed files
- acceptance criteria
- validation commands
- expected failure class
- 最終採用diff

### Phase 4: Runova軌跡収集

同じタスクを次で実行する。

- ベース7B単体
- ベース7B + Runova
- 高性能Web AI教師
- 教師提案 + Runova検証
- VariationalLoRA適用7B

これにより、モデル差とRunova効果を分離する。

### Phase 5: SFT / QLoRA

最初はRTX 3060で扱えるQLoRAを使う。

初期候補:

```yaml
base_model_size: 7B
quantization: 4bit_nf4
training: qlora
sequence_length: 1024-2048
micro_batch_size: 1
gradient_accumulation: 8-32
gradient_checkpointing: true
precision: fp16
```

学習対象:

- ツール選択

- failure class分類
- 修復方針
- rollback判断
- escalation判断
- 小さなパッチ生成

最初から万能なコードモデルへしない。

### Phase 6: 選好学習

同一タスクの複数軌跡を比較する。

好ましい例:

- 少ない変更でテスト成功
- 不変条件を守る
- 適切に追加観測する
- 同一失敗を避ける
- 無理な場合に昇格する

好ましくない例:

- テスト削除
- エラーの握り潰し
- 許可外変更
- 大規模リファクタリングへの脱線
- 同じパッチの反復
- 根拠のない完了宣言

### Phase 7: Verifier-guided RL

SFTと選好学習で基礎が成立した後に限定的に行う。

報酬例:

```text
+5 対象テスト成功
+3 関連テスト成功
+2 allowed files順守
+2 acceptance criteria充足
+1 少ない試行で完了

-2 同一失敗反復
-3 コンパイル失敗を放置
-5 既存テスト破壊
-5 許可外ファイル変更
-8 テスト削除・弱体化
-8 成功していないのに完了宣言
```

曖昧なAI採点より、機械的なVerifier報酬を優先する。

### Phase 8: 世代更新

更新されたモデルをRunovaへ戻し、同じ固定ベンチマークで再評価する。

- 自力成功率
- Web AI昇格率
- 平均試行回数
- 破壊的失敗率
- 時間
- VRAM
- 経路独立性

改善が確認できたモデルだけを次世代とする。

## 10. RTX 3060での設計原則

### 10.1 同時実行を増やさない

- WIP=1
- LLM request concurrency=1
- 学習と推論を同時実行しない
- Androidビルドや大規模テスト時はモデル常駐を調整する

### 10.2 長大コンテキストで補わない

7Bモデルへリポジトリ全体を渡さない。

Runovaが次を選別する。

- task contract
- repository map
- 関連symbol
- 関連コード断片
- 直近の失敗
- acceptance criteria
- 実行可能ツール

通常の推論コンテキストは4K〜8K程度から測定し、必要な場合のみ増やす。

学習は1K〜2Kから開始する。

### 10.3 モデルより入力構造を改善する

7Bの能力不足を、無制限な再試行、巨大prompt、複数モデル討論で隠さない。

優先順:

1. タスクを小さくする
2. 不要コンテキストを除く
3. 出力をJSON Schemaで拘束する
4. テスト結果を分類する
5. failure memoryを使う
6. 学習データへ戻す
7. それでも不足する場合だけモデル変更を検討する

## 11. 失敗可能性と反証条件

### 11.1 VariationalLoRAが効かない

FEMとの構造的アナロジーが美しくても、LLM性能へ寄与しない可能性がある。

反証条件:

- CがBを上回らない
- CがDを上回らない
- 効果がseed間分散内
- 数値整合性や経路独立性が改善しない

この場合は結果を受け入れる。

### 11.2 ゲートが実質固定のまま

高LRでも`quad_weights`が意味のある非一様性を持たず、入力依存性が性能へ寄与しない可能性がある。

対策:

- gate LR倍率の実験
- 初期化の検討
- warmupの分離
- ゲートの分布・entropy監視
- CとDの厳密比較

ただし、効果がなければゲートを複雑化し続けない。

### 11.3 Runova専用に過学習する

特定リポジトリ、特定ツール名、特定エラー文だけを暗記する可能性がある。

対策:

- リポジトリ分割によるtrain/test分離
- タスクテンプレートの言い換え
- 未知のプロジェクトで評価
- symbol名やファイル名を変えた評価
- 経路独立性評価

### 11.4 教師モデルの癖を模倣するだけになる

教師の文章形式やツール選択を模倣しても、実行結果への適応ができない可能性がある。

対策:

- 教師出力を必ず実行検証
- 複数教師候補
- 不採用軌跡も保存
- Verifier結果を中心に学習
- 同じタスクで異なる成功経路を含める

### 11.5 自己改善が自己汚染になる

モデル自身が生成した低品質軌跡を再学習し、誤りを強化する危険がある。

対策:

- 採用データはVerifier通過必須
- データセットversion管理
- teacher、self-generated、human-approvedを区別
- holdout benchmarkを学習へ混ぜない
- 世代ごとにrollback可能にする

### 11.6 一日放置すると迷走する

モデルの能力が上がっても、長時間実行では状態破損、プロセスハング、無限修復が起こり得る。

対策はモデル学習ではなくControllerで行う。

- timeout
- retry limit
- same-failure limit
- heartbeat
- checkpoint
- recovery state
- BLOCKED停止

## Appendix B. 用語

### AtomicTask

一つの目的、一つの検証可能な完了条件を持ち、単独でrollback可能な最小実装単位。

### Evidence Packet

Web、DOM、公式文書、外部APIから取得した情報を、出典、取得日時、対象version、有効期限とともに固定したデータ。

### Runova Controller

LLMとは別に、タスク状態、timeout、retry、checkpoint、verification、commitを決定論的に管理する部分。

### LLLM

本構想では、独自LoRA研究だけでなく、Runovaで高度な実装推論を担う7B級ローカルモデルの育成プロジェクト全体を指す。

### VariationalLoRA

連続経路と離散経路を、形状関数と求積重みに対応する動的ゲートで結合する独自低ランクアダプタ。

### 経路独立性

同じ問題を異なる言い換え、手順、中間表現で与えても、同一または整合した結論へ到達する性質。

### 昇格

ローカルモデルの権限や試行範囲を拡張することではなく、解決不能な設計問題を静的なWeb AI再設計へ送ること。
